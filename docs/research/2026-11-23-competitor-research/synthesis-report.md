# 执行摘要

本报告合并并交叉校对了 4 份相互独立完成的竞品调研样本（2 份 Claude Code / DeepSeek V4.1 Flash、2 份 Antigravity / Gemini 4 Neon），覆盖国内 4 款产品（**即梦、可灵、海螺、Vidu**）与海外 5 款产品（**Runway、Midjourney、Lovart、Luma Dream Machine、Recraft**），并结合 2026-11-23 直接查阅的火山方舟官方模型与 API 文档，对四份样本中的事实分歧做了权威口径对齐。

### 五项核心结论

1. **原提案模型基线与价目表已失效（4/4 共识 + 官方文档证实）**：火山方舟 `doubao-seedance-1-0-lite` 已下架，`1.0 pro / pro fast` 已标注「即将下线」，当前主力在役模型为 **Seedance 2.0 / 2.5**。原提案 `lite 720p 5s = 10 积分`（实收 ¥1.39~¥1.99）低于 `2.0 mini 720p 5s` 成本 ¥2.48；`pro 720p 5s = 30 积分`（¥4.16~¥5.97）覆盖不了 `2.5`（¥7.56）和 `2.0 1080p`（¥12.39）；按像素平方折算 `pro 1080p 10s ≈ 135 积分` 直接击穿标准月卡 100 积分上限。
2. **纯客户端轮询转存是最大工程缺口（4/4 共识）**：原提案拒绝 webhook/cron，仅在 `GET /api/video/[id]` 中同步下载转存 MP4 并惰性判 30 分钟过期。用户提交后关页超 24 小时会导致方舟临时链接失效、视频永久丢失且平台白付算力并向用户退款；3 秒轮询与多标签重入还会触发重复转存或 Serverless 超时误退。经官方 API 文档核实，方舟原生支持 `callback_url` 回调，应采用「**回调为主 + Cron 巡检兜底 + 前端退避轮询加速 + 原子状态锁 `transferring` + 3 次流式转存重试**」架构。
3. **存在 5 处高危资金、并发与安全边界漏洞（四方互补发现）**：
   - 订阅池跨周期失败退款按原池回填，会在下次读路径被立即清零（4/4 共识）；
   - 惰性 30 分钟过期若未在 `submit_video_task` RPC 计数前先清理，僵尸任务会永久锁死单用户 3 并发槽位（Gemini #1）；
   - `POST /api/video` 缺少 `Idempotency-Key` 唯一幂等约束与 `createTask` 网络超时未知态处理，易致重复扣费（Claude #1/#2）；
   - 将 `--duration`/`--resolution` 拼接到 `text` 末尾存在提示词参数注入风险，官方 API 实际支持顶层结构化 JSON 字段（Gemini #2）；
   - 火山方舟个人账号默认并发约 3、企业约 10，若无全站并发闸门且将上游 `429` 计入 `provider-health` 熔断窗口，会误杀全站提交（Gemini #2）。
4. **资产串联与输入画质存在明显断层（4/4 共识）**：提案只做了 `/video` 内部反向选图，缺少从历史图库、经典生成结果、Agent 画布一键推送到 `/video` 首帧的正向入口；本地上传首帧沿用 1024px JPEG 会折损高清视频清晰度，1 小时 signed URL 存在排队过期风险；视频存入公共 bucket 有盗链与流出流量失控风险。
5. **PixGen 的差异化应押在「Agent 精修图 → 一键图生视频 + 双池透明计费 + 失败必退承诺」**：即梦正在以低于方舟刊例价的补贴价打价格战，PixGen 不应跟进低价或盲目堆叠 72~144 种参数组合，而应收敛为清晰的画质预设档位，先把首帧闭环、资金不变量与高确定性体验打穿，二期再将视频能力接入 Agent 画布与首尾帧。

## 1.2 原 `add-video-workbench` 提案的合理骨架 vs 结构矛盾

- **原提案已守住的正确骨架**：独立 `video_generations` 表与 RLS；提交时单事务原子预扣 + `credits_sub_split` 池间拆分快照 + 失败逐池退款；服务端单一价目来源；复用 `provider-health` 熔断；`VIDEO_PROVIDER=mock|seedance` 全链路可测且生产禁用 mock。
- **原提案暴露的结构矛盾**：
  1. 沿用 `Seedance 1.0 lite/pro` 模型与 `10 / 30` 积分占位价，与在役 2.0/2.5 成本倒挂，且未按 SKU 能力表门控 1080p；
  2. 开放 `2 档 × 2 时长 × 3 分辨率 × 6 比例 × 2 模式`（72~144 组合）全排列，而单条高配 135 积分超标准月卡总额；
  3. 仅依赖客户端 3 秒轮询完成转存与超时判断，无服务端回调/巡检、无提交幂等、无取消机制、无跨周期退款保护；
  4. 状态机命名在 `design.md`（`queued|running`）与 `spec.md`/`tasks.md`（`pending`）间不统一；
  5. 免费 5 积分用户可进未加锁的 `/video` 却点不动默认 10 积分档位，体验断层。

- **双轨积分是行业绝对共识**：除 Midjourney（GPU 时长 + 无限 Relax + $4/h 加购）外，即梦、可灵、海螺、Vidu、Runway、Lovart、Luma、Recraft 全部采用「**月度到期清零订阅池 + 长有效期/永久充值包**」，且扣费顺序均为「短有效期/订阅池优先」。PixGen 数据库双池模型本身完全正确，仅在商业层因下架积分包产生了补给缺口。

### （2）PixGen 单位经济与原提案 10/30 积分倒挂测算

PixGen 现有 4 档会员每积分实收（不含约 0.6% 支付通道费、税费与存储/CDN 成本）：
- 标准月卡（¥19.9/100）= **¥0.199/分**；标准年卡（¥199/1200）= **¥0.166/分**

- **10 积分**最高收入仅 ¥1.99（Pro 年卡 ¥1.39），在所有在役 Seedance 2.x 的 720p 档位上**全部负毛利**（`2.0 mini` 成本 ¥2.48 即每条净亏 ¥0.49~¥1.09）；

- **135 积分（pro 1080p 10s）**不仅直接超出标准月卡 100 积分总配额，在 `Seedance 2.5`（成本 ¥37.42）上按 Pro 年卡口径（收入 ¥18.77）**单条亏损 ¥18.65**；

### （3）三大商业结构冲突与破局路径

1. **高规格击穿 100/300 会员额度**：竞品单条视频常规占入门月卡额度的 5%~15%（可灵 5.3%~10.6%、Runway 4%~9.6%），每月可产 15~40 条；而 PixGen 若在不动会员体系前提下以 30% 毛利覆盖 `Seedance 2.0` 1080p（需 ~125 积分/5s），标准月卡连 1 条都点不动。
   - **短期最优解（不动会员体系前提）**：首期聚焦 `Seedance 2.0 mini`（480p 12 分 / 720p 25 分）+ `Seedance 2.0`（720p 50 分，10s 100 分），全矩阵 Pro 年卡毛利守住 **~28.5%~30.5%**（标准月卡 ~50%），最高单条不超 100 分，暂缓开放 1080p/4K；
   - **中期演进**：观察首月视频消耗后，向**有效期内会员**开放独立加油包或新增 Pro+/工作室高额度档位，承接重度用户的月内脉冲复购。
2. **免费 5 积分与 `/video` 无门禁脱节**：若免费用户可进 `/video` 却一条也点不动，转化效率低于明确门禁。与 Agent 统一设为**会员专属**（非会员可浏览工作台参数、锁标与示例，点击提交引导 `/upgrade`）是成本与转化最清晰的选择；未来若推拉新活动，再单独设计「一次性带水印 480p 体验券」，避免每日免费视频被薅。
3. **双池透明度与过期退款保护**：
   - 提交前显式展示双池拆分预览（如「本次消耗 25 积分：优先扣订阅池 25，剩余 75」）；
   - `refund_video_task` 必须判定 `sub_credits_expires_at`：未过期回订阅池；**若原订阅池在任务执行期间已过期，必须自动改退永久池 `credits` 并写入 `video_refund_redirected` 审计事件**，杜绝「账面退款、读路径瞬间清零」。

## 3.2 图像历史 ↔ 图生视频首帧串联与资产管理

四份调研一致指出：**「先用经典模式或 Agent 对话把图片打磨到位，再一键变成视频」是 PixGen 相对纯视频工具最真实的差异化链路**，但原提案在串联与画质上有四处缺口：

1. **缺「推（Push）」入口（P1 核心杠杆）**：Midjourney（图片卡 `Animate`）、即梦、可灵、Lovart 均以图片为起点正向推进。PixGen 需在 `/history` 图像卡、`/generate` 经典结果区及 **Agent 画布单图工具栏**全部增加「生成视频」快捷按钮，携带 `firstFrameId` 跳转 `/video?mode=i2v&firstFrameId=<id>` 并经服务端归属校验预填首帧与 `adaptive` 比例。
2. **1024px 首帧压缩与 1 小时 Signed URL 双隐患（P0/P1）**：
   - 本地上传首帧沿用 1024px JPEG 会在高清视频输出中造成人脸/文字/产品 Logo 糊化；应与经典参考图解耦，放宽至最长边 **1920px**（≤8MB），且官方 API 原生支持 `data:image/jpeg;base64,...`（<30MB），本地上传可直接走 base64 提交，彻底规避外链拉取超时；
   - 历史图片传给方舟的 signed URL 应由 1 小时延长至 **24 小时**，避免高峰排队超 1 小时导致拉图 403 失败；同时保存轻量首帧封面缩略图，防止源图删除后血缘断链。
3. **公共视频 Bucket 的盗链与流量风险（P0）**：视频单文件 5~50MB，公共 bucket 会造成付费视频外链传播与 Supabase 流出流量账单不可控。必须改为**私有 `generated-videos` bucket** + 鉴权后签发短期播放/下载 URL；`history-grid` 混排视频卡必须采用 **`poster` 封面图 + `<video preload="none">`**，严禁在列表首屏同时预加载多条 MP4。
4. **首尾帧与多参考演进预留**：方舟已支持 `first_frame`、`last_frame`、`return_last_frame`，首期不开放 UI 但库表应采用结构化 `frame_inputs jsonb`（而非写死单帧字段），为二期零迁移上线首尾帧与尾帧续写留口。

## 3.3 异步生成等待、任务流、并发风控与资金不变量

对比行业实践（服务端 Worker + 回调 + 分层并发 + 明确取消/重试语义），原提案需补齐 7 项核心工程机制：

1. **双通道任务推进（Callback + Cron + 退避轮询）**：
   - **主通道**：接入方舟原生 `callback_url`（带 HMAC-SHA256 签名），收到回调后服务端以 API Key 反查方舟任务接口核实真态（不盲信回调体），再触发统一推进器；
   - **兜底通道**：配置定时巡检（如每 5 分钟扫描活跃超时/滞留任务），彻底消灭「用户关页 24h 后临时链接过期导致视频丢失 + 平台白付算力」；
   - **交互加速**：客户端仅做退避轮询（前 30s 每 3s → 30s~2m 每 5s → 2m 后每 10s，页面不可见暂停）。
2. **统一状态机与原子转存锁 + 流式重试**：
   - 统一全链路状态枚举为 `queued → running → transferring → succeeded | failed | expired`（彻底消除 `pending` 与 `queued/running` 混用）；
   - 通过 `claim_video_transfer` 原子抢占 `transferring` 状态锁（并设 2 分钟租约防进程崩溃死锁），消除 3s 轮询/多标签/回调并重触发重复下载上传；
   - 流式下载上传设硬大小上限（如 100MB）；网络抖动失败时在 24h 窗口内最多**重试 3 次**，耗尽再退款，避免把方舟已扣真钱的成功视频一次误杀作废。
3. **提交幂等与超时未知态**：
   - `POST /api/video` 强制带客户端 `Idempotency-Key` 并建 `unique(user_id, idempotency_key)` 索引，防止网络重试/双击双扣；
   - 明确 `createTask` 超时/失败路径的幂等回滚或核查策略。
4. **僵尸并发槽位清理 + 全站并发闸门 + `429` 隔离熔断**：
   - 在 `submit_video_task` RPC 校验单用户 `>= 3` 并发之前，**先原子清理该用户超过超时阈值的僵尸活跃任务并退款**，避免关页遗留任务永久锁死 3 并发槽；
   - 增加全站活跃任务上限闸门（适配个人账号并发 3 / 企业账号并发 10）；
   - `provider-health` 仅对 `401/403`/欠费/连续 `5xx` 触发全局 503 熔断，**上游 `429` 限流严禁触发全局熔断**。
5. **结构化 JSON 传参防注入**：
   - 严禁把 `--duration`、`--resolution` 等 flag 拼在用户 `prompt` 尾部（防提示词注入篡改计费规格）；改用方舟顶层结构化 JSON 字段传递全部控制参数。
6. **上游超时对齐与取消/迟到成功语义**：
   - 提交时显式传 `execution_expires_after: 3600`（方舟允许最小值 1 小时，取代默认 48 小时）；
   - 应用层 30 分钟判 `expired` 时 best-effort 调用 `DELETE /api/v3/contents/generations/tasks/{id}` 取消 `queued` 任务；
   - 若已退款后收到迟到成功回调，仅写 `late_succeeded_at` 供财务对账，不回写终态也不补扣。
7. **错误分类、等待反馈与参数复用**：
   - 区分 `content_moderation`（审核拒单：引导改词/换图，不鼓励无脑原样重发）、`provider_error`、`transfer_failed`、`timeout`；
   - 活跃任务卡明确展示阶段（排队中/生成中/保存中）、已等待计时与「可离开页面，稍后在历史查看」；
   - 所有终态卡片（含成功、失败、过期）均提供「复用参数回填创建区」按钮，适配视频高频微调抽卡场景。

## 4.4 过度设计 vs 欠设计速查

| 类别 | 具体项 | 结论 |
|---|---|---|

## 5.3 验证边界与上线前必做实测清单

本报告中竞品定价、模型成本、API 能力均基于 2026-11-23 公开文档与网页采集，**未登录任何第三方付费账号，也未在 PixGen 生产方舟账号下实发扣费调用**。在视频工作台切生产流量前，仍须在火山方舟控制台逐项实测确认以下 4 项：
1. **账号认证与并发配额**：确认生产 Key 归属已完成企业认证的按量付费账号（并发配额 ≥10），按实测值配置 `VIDEO_MAX_GLOBAL_ACTIVE`。
2. **真实单价与 Token 账单抽样**：用预发环境实跑 1 条 `preview`（`2.0 mini 480p 5s`）与 1 条 `standard`（`2.0 mini 720p 5s`），核对返回的 `usage.completion_tokens` 与方舟账单实扣金额是否与 `¥1.16 / ¥2.48` 刊例价一致。
3. **回调与取消实测**：实测 `callback_url` 公网到达延迟、HMAC 校验、`execution_expires_after: 3600` 生效情况，以及 `DELETE` 取消接口对 `queued` 任务的状态返回。
4. **端到端转存与播放兼容**：实测 720p 10s MP4 在部署区域拉取并流式转存至 Supabase 私有 bucket 的耗时与文件大小，验证桌面/iOS/Android 浏览器内联播放与下载兼容。
